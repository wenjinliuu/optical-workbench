# V0.24 旧件处置与实际转出

固定原售后案例、原订单行、退回接收记录；可以使用尚未安排维修的原件，或维修复检合格/不合格批次的剩余原件。已开始但未复检的维修不直接转出处置。

申请明确本次数量、报损转出或退供转出、实际去向及检查依据。负责人独立执行审核动作，可以批准或驳回；前台/负责人可以撤销尚未转出的申请。批准保留旧件保管，须在原案例实际处理中明确登记实际接收人、批准之后的转出时间、凭据编号及说明，才完成整批转出。分批操作通过分别申请明确数量，不改已有申请来源。

待审核、已批准和已转出的申请占用固定原件来源数量；驳回/撤销释放占用。维修安排、返工和原件归还读取同一来源可执行余额，数据库阻止重复消耗。当前售后保管=累计接收−原件归还−实际处置转出；批准不扣保管，实际处置不增加原客户再次退回容量。正常商品库存/预留、原订单金额、收款和新商品交付不因旧件处置改变。

## 接口与共同保护

- GET/POST `/api/aftercare/cases/:id/dispositions`：完整数量、有界列表及可用固定来源；POST提交检查及申请。
- GET `/api/aftercare/dispositions/:id`：不可变来源、当前状态和有界历史。
- POST `/api/aftercare/dispositions/:id/events`：approve/reject/cancel/execute；每次均提交expected_case_revision、expected_work_revision、expected_sequence及expected_revision。

员工读取限本店客户；前台/负责人录入与实际转出，负责人审核，专业岗位只读处置安排，家长不可读取内部记录。实时会话、首次改密、严格字段、数量/时间范围、幂等、防并发与审计在同事务核对；冲突重读保留原批次、检查依据、去向和转出填写。案例暂停/关闭阻止实际转出，明确恢复后继续；未转出申请仍可明确驳回/撤销以释放占用。

021新增不可变aftercare_disposition_events、aftercare_work_disposition_refs。处置捕获当时案例及维修版本，维修捕获处置序列，旧schema20升级仅为原维修记录增加序列0引用。原表和原migration不改。恢复核对全部引用覆盖、连续状态、固定批次/数量及跨记录先后顺序，包含相同毫秒记录，拒绝缺失引用或篡改去向；客户时间轴和库存详情使用同一保管投影。

## 继续边界

退供转出只记录实际交接，供应商签收、索赔赔付和外部通知另行办理。报损实物转出不计算费用、损耗金额或财务分录；退款、专业方案批准和旧件转可售须按真实规则接续。本轮虚构记录覆盖待审核、批准待转出、实际报损转出三个阶段，明确标识来源，不代表业务验收完成。
