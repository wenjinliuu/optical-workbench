# V0.45 原批实际在库与仓位核对

从已匹配入库的原收货，负责人记录已发生的原件身份、数量、可用或隔离保管范围、实际位置、位置与原件对应的来源、核对UTC时间及下一步。原商品版本、计量单位和原收货资料固定。未匹配超收原件仍走独立超收流程。

观察数量是当时人工核对事实，不是今天该批余量；多个观察不能累计为可售或独占分配。原入库量只是数量上限，不证明旧原件今天仍在库。此版本建立后续明确批次/仓位分配所需的事实基础，完整分配和销售批次选取仍待后续。

观察须原收货已实际入库，数量不超过原匹配量减该原收货已实际退供量，也不超过当前SKU对应实物范围。可用观察还不得占用本原收货受质量保护的数量：同SKU另一箱可用库存不能让被保护的原隔离批被记录成可用。隔离观察不自动复检或放行；库存预留、调拨、出库及资金均不由观察自动触发。

新发生观察追加新版本，保留旧实际时间/原身份数量位置/资料和库存引用。明确撤回本版观察解释是更正，不注销实际到货或处置实物；撤回后可重新实际核对追加版本。后来原资料、SKU库存、销售出库、实际退供或质量保护来源变化，旧观察保留并标记引用已变化，下一步须实际重新核对并明确采用当前来源。原填写保留，不能静默替换。

## 入口、API与权限

原采购收货详情选择“原批实际在库与仓位核对”。负责人真实填写事实，前台/专业人员只读，不代表正式仓库资质；当前门店、角色、会话和密码重置在正文读完后重新校验，家长及跨店拒绝。

GET `/api/purchase-receipts/:id/custody` 工作区；POST `/api/inventory-custody` 创建原核对记录；GET `/:id` 读取本版和历史，POST `/:id/observations` 追加新实际观察，POST `/:id/events` 明确withdraw撤回解释。观察写入固定expected_source、当前核对序列、原记录版本和修订；正向事实在重试缓存前和提交时均校验当前来源。默认30条，最大100条，后续页同时固定expected_sequence与expected_source，原观察版本用数值version。

手填位置来源与原收货旧location_note分别保存，现场核对不会更改旧收货资料；真实地点和原件身份依据必填，不补造通用仓位、质量政策或专业结论。

## 数据与恢复

schema41追加八表：inventory_custody_roots、versions、events及stock/dispatch/receipt/return/quality五种原业务上下文。上下文捕获当时核对序列，观察捕获当时原资料、库存序列、实际出库/退供修订和质量序列。同毫秒也能核对互相采用先后，旧schema40只对空新核对账补技术零前缀，不补旧批次今天保管量。

原生触发器限制当前真实权限、原入库/实际范围/保护数量、数量时间上限、连续版本/记录、观察配对、明确撤回、原业务和核对时间关系、文本和不可变历史；根/观察/事件、审计及重试缓存事务回滚。恢复在当时原前缀重新核对数量和质量保护，保留原销售及退供快照；173表CLI重复、备份核验和独立恢复逐表一致、会话清零。

六独立虚构阶段各自使用新商品、原采购及收货：可用实际核对、隔离实际核对、核对后库存变化、核对后原资料更正、解释撤回、撤回后重新核对。旧业务行和SKU余额保留，不把原位置未知补成新位置；22专项覆盖实际来源、保护、销售/退供、历史分页、同刻前缀、原生/审计/重试/当前身份/正文等待、非空schema40及恢复。
