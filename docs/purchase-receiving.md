# V0.40 · 原采购分批收货、实际验收与库存衔接

T07.01 / W5-N3、W5-N4 的开发切片。采购原需求、负责人商业批准和已发生订货沿用 V0.39，收货固定该实际订货事件、原行和供应商/商品原版本。正式仓库/质量岗位资质、通用质量标准、供应商合同、付款对账与整体验收仍待实际依据。

## 实际收货与差异

实际数量与明确匹配原采购数量分别记录，匹配不能超过实际到货或该原行尚未匹配量。允许保留超收，未匹配超收量明确待处理，不记可用库存、不推定新增采购批准或付款。分批及未匹配原采购数量独立展示，不将“全部匹配”认定采购业务完成。

实际到货时间须已发生且不早于原订货，保留实际收货人和原始说明。已知供应方交货编号与原行标识成对固定并防重复；未知保持空值，仅凭人工来源说明不宣称已实现外部单据自动去重。技术幂等和每批一次入库独立保护。误录取消仅限未入库、负责人明确操作，保留原记录并释放匹配容量，不表示实物已经退供。

供应商后来停用、商品名称/售价修订不能抹去实际到货，仍使用原单位。V0.39 的实际订货单位/类别保护继续有效。实际供应方取消、退供和仓库差异处理后续分别保存真实结果。

## 原资料与验收

批号、实际效期、仓位分别标记已知/未知；效期可明确不适用并保留人工依据。来源说明/引用和每版更正依据固定，未知不预置虚构值。

本地负责人/专业角色明确记录实际检查时间、项目和逐项结果；批号、效期、仓位要求必须逐项明确，要求依据由实际来源填写，不预置通用标准或正式质量岗位资质。合格要求项目全部实际合格、明确要求资料已知，已知效期在检查时有效。不合格可保留要求资料仍未知的事实，不能假造通过。

入库前资料更正追加版本、回到待验收，旧检查仍固定旧版。入库后资料更正保留已入库状态，不改写原验收、库存事件或自动解除隔离；质量重分类、召回、数量纠错与供应方退供属于后续明确实际库存结果。

## 一次性入库

负责人手工选择可用或隔离状态。可用入库须当前原资料的明确合格验收且实际已知效期仍有效。待验/不合格可以明确隔离入库并保留实际隔离依据，不产生虚构专业放行。

每批只入账完整匹配数量一次，未匹配超收部分保留待处理。复用 inventory_events：可用为 receive，隔离为同一事务的 receive + isolate，记录原事件引用；事务期间不暴露暂时可用状态。不新建平行库存数量账、不自动预留/收款/付款/退款、不自动结束采购。

固定收货资料/验收事件、入库前库存序列和实际出库序列。页面/原生约束与恢复核对共同保护来源、数量、状态和原库存引用；业务写入、库存、审计和幂等同事务。普通库存手工入库保留原独立来源，不冒充采购验收完成。

## 技术入口和演示

schema37 四表：purchase_receipts、purchase_receipt_versions、purchase_receipt_events、purchase_inbound_refs。原采购详情“分批收货与验收”入口，保留完整数量/历史、有界分页、具体原版本、并发来源冲突的未提交内容及退出清理。家长和跨店拒绝；前台登记到货资料，负责人/专业登记验收，负责人入库/取消误录。

API：GET /api/purchases/:id/receipts；GET/POST /api/purchase-receipts；GET /api/purchase-receipts/:id?version=N；POST /api/purchase-receipts/:id/versions、/events。使用原收货序列、原记录修订/版本及入库前库存/出库序列。可用入库在请求体读取后及幂等响应前重新核对来源。历史检查与库存引用不会跟随新资料改变。

四个独立虚构采购/收货场景：未知分批和超收、不合格实际隔离、合格可用入库、入库后资料更正。只追加自身采购和明确库存来源，重复初始化逐表保持已有账号、原业务、人工资料及库存流水。非空 schema36 升级不补造收货、验收或库存事件。全表备份/独立恢复核对包含四表及原库存引用。

开发检查见 test/purchase-receiving.test.mjs 和 scripts/purchase-receiving-browser-check.mjs。业务方集中体验与正式流程验收仍待后续，原 50 任务/287 要求和依赖文本不变。
