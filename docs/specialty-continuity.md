# V0.38 专项更换重订与长期来源归档

入口：客户专项详情的「专项更换与长期归档」，以及原售后重做/换货安排的「专项原产品专业来源」。沿用原实际签收、原售后、新独立订单、明确原单价、商业安排、退回件保管/维修/处置、实际收退款、加工、批号、护理、质检、签收与出库，不建立第二套商业账。

## 独立专业采用

商业负责人批准既有重做/换货安排；独立新专项当前专业责任人另外核对此原实际签收产品当前已确认的具体反馈版本和明确继续/调整意见，以及新单的专项评估、该评估版本的同意和已核对的原参数。商业与专业确认可分别办理，实际新单执行须二者有效且原售后处于办理中。原专项已停用也不会被新单采用恢复，新需求用明确的新专项来源。

原签收、原专项、原售后和独立新单固定；每次专业批准可明确选择新的反馈条目，专业记录保存原反馈版本、原专业意见、独立新单批准和当时的临床/参数/复查/原检查/外院序列。当前责任、同意、反馈、材料或参数变化，后续执行停止，重新核对后追加专业采用；关闭同一已确认反馈不会抹去原意见。撤销专业采用不作退款、收回已交付产品或更改历史。

共享请求门禁在幂等响应读取前重核专业来源；SQLite 原生门禁也覆盖未关联专项的新单。受保护的实际预留、收款、工单建立/安排/开工/完成、合格质检/返工/签收和出库固定当时的专业采用事件。已发生到货、不合格事实、释放、明确误录更正和原实际退款继续依既有规则办理。护理要求仍按明确原来源，不能从更换自动推定已掌握。

## 不可变归档

归档保存原条件版本、相关临床和同意版本、原单与关联新单、原批号/护理/复查、售后和新单商业/专业历史、实际退款来源、质检/签收/出库的来源索引。保存当前状态、人工说明/依据/下一步，以及仍待继续的护理、复查、售后和更换安排。

每张追加来源表固定保存当时最大 rowid；相同毫秒后追加的新事实不会替换旧归档。索引 SHA256 与完整来源前缀在备份核验/独立恢复时重新构建比较。归档不停止临床、不结清订单/资金、不结束原售后，不自动完成复查或家庭授权；金额和库存实际事实继续以原账为准。来源索引超过 1MiB 会明确拒绝，不能截断。

## 升级和未知历史

schema35新增五表：specialty_continuity_boundary、sources、events、execution_refs与specialty_archives（后四者完整名称以迁移为准）。迁移保存升级前售后新单操作的技术 rowid 边界；旧操作逐表保留，缺少专业采用的旧历史明确未记录，不伪造批准或执行引用。后续受保护动作必须满足新门禁。已经执行而未记录专项的新单不能绕过已有「专项初次关联须未执行」规则补造历史；需要按真实来源明确迁移方案或独立未执行的新单。本地虚构数据不代替该决定。

GET /api/specialty-continuity/cases/:case、plans/:plan；POST /api/specialty-continuity/plans/:plan/events明确approve/revoke。POST /api/specialty-archives保存当次原来源；GET /api/specialty-archives/:id读取具体不可变索引。门店/内部权限、实际当前责任、会话、CSRF、严格字段、来源修订/序列及事务审计共同核对。历史分页保持完整总数；来源冲突保留填写但阻止静默替换依据。客户时间轴可定位专业采用和具体归档。

## 虚构展示和边界

三个独立新单展示待专业采用、原实际加工/批号/质检/签收/出库贯通、原专项停用后新单采用撤销。三个归档保存更换前、后和原停用专项来源，既有记录全部保留，重复初始化不覆盖人工办理。

验证入口：test/specialty-continuity.test.mjs、scripts/specialty-continuity-browser-check.mjs、CLI备份核验和独立恢复。当前T06.04/W4-N6为部分实现，真实专业职责/机构资质、完整表单、长期保留政策、正式供应商/质量责任与业务验收仍需实际来源。下一主线进入T07.01供应商与采购；继续使用原共享商品、库存、加工到货及售后退供来源。
