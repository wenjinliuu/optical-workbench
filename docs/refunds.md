# V0.25 原实收退款

本地开发记录流程：有效原实收 → 人工退款申请 → 负责人批准/驳回 → 登记已发生退款；未实际退款前可撤销。批准不表示支付发生，系统不连接支付渠道，也不自动按商品/优惠/维修费用计算退款。

金额精确到分；每份申请固定原订单版本、原收款记录、退款金额、决定依据和可选对应原售后案例。部分原款退款可分开申请，每份批准金额实际登记一次；需要修改金额时先撤销再独立申请。每笔原款的已退、待审核和已批准申请合计不得超过有效原实收；驳回/撤销释放申请占用，实际退款不可撤销或删改。每店同方式与凭据编号只能登记一次实际退款。保留实际接收人、规范UTC时间、凭据和说明，实际时间须不早于批准和原款收到时间。

原有效实收不覆盖/作废为退款。待审核/已批准/已实际退款保护原收款免于误录作废；拒绝/撤销且无其他占用后可按独立误录流程纠正。原有效实收仍保护订单历史版本，全部退款也不会自动取消、修订、出库、归还旧件或结束售后。

可选案例必须属于同一客户/门店及原订单，或已固定同一新订单版本的重做/换货案例；关闭案例仍可作为财务历史来源，不会因此自动重新开始。每次退款操作捕获当前案例版本；原案件状态与专业结论独立。

## 接口和权限

- GET /api/refunds：本店资金授权查询，q/status/limit(1–100)/offset；完整数量、受限分页，状态pending/approved/rejected/cancelled/executed。
- GET /api/retail/orders/:id/refunds：当前原实收、独立退款投影、可选原款/案例和申请历史。
- POST 同路径：receipt_id、amount_cents、case_id(null或ID)、decision_basis、note、reason；必须携带expected_order_version、expected_payment_revision、expected_sequence、expected_case_revision(null或当前关联案例版本)。
- GET /api/refunds/:root：固定申请、分页历史、当前原实收和原案例。
- POST /api/refunds/:root/events：上述共同版本字段、expected_revision、action(approve/reject/cancel/execute)、note、reason；execute另带method(cash/card/transfer/other)、reference、receiver_name、refunded_at、receipt_note。

负责人/前台读取及申请、撤销、实际登记；批准/驳回仅负责人。专业人员和家长不能读取资金记录及退款时间轴。服务端实时校验门店、角色、会话及首次改密；原款、全订单退款序列、单申请和可选案例版本共同保护并发，幂等响应与审计同事务。客户端冲突重读保留金额、来源、案例、依据及实际凭据，失效来源需重新核对；退出清空内容并阻断迟到响应。

## 历史、恢复和演示

schema22的refund_events是不可变申请/动作流水；payment_refund_refs捕获每次原收款操作所见退款序列，跨资金顺序在同一毫秒也可独立恢复回放。旧schema21升级不补退款或改变原表行，原收款只增加明确序列0引用。备份/恢复核对金额、来源、连续版本、状态转换、实际凭据唯一性与交叉顺序；篡改拒绝恢复。

新增3申请6事件和待审核/已批准/实际已登记三阶段虚构样例，旧资金5记录、库存18流水、旧件维修/处置保持，重复初始化不覆盖手工记录。原实收减实际退款为“按记录暂留金额”，不作为收入、应收或到账证明。优惠分摊/费用公式、正式票据、到账核验、交班、专业资质和生产部署继续独立办理；350项自动检查与11组浏览器不替代业务验收。
