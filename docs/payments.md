# 基础收款记录 · V0.18

T04.02的本地开发切片，原任务、依赖和整体验收保持。负责人/前台登记已经发生的收款；金额不是渠道核验结果，也不自动确认专业处方、订单成交或加工完成。

## 原订单与金额

每笔记录固定order_id、order_version、customer_id、store_id、当时商品明细合计basis_total_cents及CNY。实际金额独立登记为整数分，范围1至10^12分；有效金额合计不超过10^14分。按本单实收登记，分次记录不分配到商品、优惠、订金或尾款状态。允许金额高于原明细合计，并显示带符号的比较差额，避免把未确认规则变成应收门禁。

订单区显示有效手工登记金额和笔数、当前明细合计及比较差额；差额不作为欠款、营收或应收核算。历史记录保留旧订单金额依据，当前状态明确标示为当前订单。存在任一有效登记即禁止修改或取消原单，API和数据库触发器共同保护。库存释放不会解除资金保护，作废误录不会移动库存。

## 收款与误录纠正

方式cash/card/transfer/other仅描述手工记录来源；可选外部编号最多120字，实际收款时间为2000年之后、不晚于登记时间的规范UTC时间，登记时间由服务端生成。必须填写依据。相同门店、方式和外部编号只能有一笔有效记录，跨订单并发仍只能成功一笔。无外部编号也使用同意图幂等键保护重试。

负责人可追加void纠正“未实际发生/重复或错误录入”的记录；source_id必须指向本单有效receive，金额、方式、编号、实际时间和原单版本由服务端复制，一笔只能作废一次。原记录不可修改/删除，记录和来源互相展示。经负责人纠正后，同外部编号可重新正确登记，旧历史保留；不能把此动作当作真实退款或支付撤销。实际退钱、退款审批、商品分摊、票据、交班和应收仍由后续正式规则实现。

## 权限与接口

| 请求 | 岗位 / 内容 |
| --- | --- |
| GET /api/payments?q=&action=all/receive/void&limit=50&offset=0 | 本店负责人/前台，按订单单号、客户姓名、外部编号字面检索；完整记录数、有界分页，不提供营业额统计 |
| GET /api/retail/orders/:id/payments?limit=50&offset=0 | 同上；当前金额依据、有效登记、保护状态、完整历史数量及分页 |
| POST /api/retail/orders/:id/payments/receive | 同上；expected_order_version、expected_revision、amount_cents、method、reference、received_at、reason |
| POST /api/retail/orders/:id/payments/void | 仅负责人；expected_order_version、expected_revision、source_id、reason |

写入要求登录、改密完成、有效门店权限、CSRF和幂等键。事务内复核会话与当前订单/收款版本，任何陈旧请求409；取消原单拒绝登记；审计失败和幂等保存失败与业务一起回滚。不同意图复用同键409，同意图重试返回原结果。专业人员和家长拒绝资金接口，其他门店原单404。客户时间轴只向有收款读取权限的岗位投影receive/void，明确固定订单版本，按登记时间和记录序号稳定分页。

## 页面、展示与恢复

侧栏“收款记录”检索、类型筛选、完整计数、分页和固定原订单入口。订单详情登记本次收款、查看原记录与误录纠正；历史订单只读。冲突重读保留金额/方式/外部编号/时间/依据，再由员工核对提交。登录会话、当前客户和请求状态隔离，退出清空记录/表单，迟到响应不能重建。原订单有库存或资金保护时修改/取消禁用，服务端仍独立拒绝。

新增虚构5条记录：原单V2两次1000/1600元登记，原单V1误录500元、追加作废、重登记实际300元；取消和仅服务订单保持未登记。再次扩展不覆盖手工收款或原数据。schema15一张payment_events表，连续revision、原版本复合外键、唯一作废来源、有效外部编号门禁和历史不可变触发器。V0.17非空升级所有原表相同，新表为空；不补造历史收款。备份/独立恢复校验连续记录、原单金额与身份、时间、作废来源和当前资金保护/编号唯一性，恢复撤销所有会话。旧快照先用对应版本工具独立恢复，再升级副本。
