# 原有效名单明确人工建档（V0.69）

T08.03 / M17-F01、D、R、A、W6-N1/2、S12。入口：原活动 → 固定原批次 CSV → 本原名单行人工关联 →「从本原行明确人工建档」。当前准备责任人同时具有原 `customers:create` 权限才可创建（负责人/前台）；专业人员不因筛查身份获得建档权限。原建档来源读取沿当前名单责任范围，家长、外店和移交前的旧责任人拒绝。

只有当前 CSV、当前未撤回且有名单处理原说明的活动、可用责任人和无授权/日期/重复编号等错误的原行可新增。员工明确复制原字段到**可编辑草稿**，核对新姓名、出生日期、联系人和电话（沿已有客户字段约束），记录资料来源、差异及建档依据；不会在读取名单时自动建档。未知资料可留空，联系人不会自动获得家长授权。原 CSV、候选和错误不覆盖。

保存前明确核对本店完整同名/同电话候选：固定每位候选的客户资料版本、完整数量及20条分页。全部页显示后才能声明「没有可采用的现有档案」，填写人工判断依据；有同名候选不视为相同身份，也不会强制合并。改动新客户四字段清除旧候选核对证明与声明，活动、责任、原行关联或客户来源变化要求明确重读和重新核对，输入保留。源字段或依据不是正式身份、监护/项目授权、临床同意或报告许可的替代。

`screening_row_registrations` 固定原活动/CSV版本/名单解析行号、唯一新 customer_id、初始资料快照、唯一原 link_id、建档前完整客户资料前缀、全部重复候选引用、原来源、人工无可采用档案声明/数量、核对/建档依据及当时角色/操作人/UTC时间。原客户初版沿既有 initial 快照，不覆写；外部/员工/家长自报来源另外固定在建档原件中。

迁移060的原生插入守卫核对当前活动/CSV/逐行授权、客户创建岗位、原来源、四字段合法性及完整候选；AFTER INSERT 在同一个 SQLite 语句中创建新客户、自动初版和原名单 link 版本。新客户和关联引用为延迟外键，但语句结束必须配对齐全。API 将这一语句与三类审计、幂等结果放在同一事务，任一失败全部回滚，不产生半份或无来源档案。原行只能建档一次；撤回 link 保留已建档客户和初版/建档原件，重新关联使用已有客户，不再建第二份身份。CSV 新版不继承关联或自动建档，需重新核对已有客户。

API `/api/screening-registrations/:project/:batchVersion/:row`：根 GET 读取唯一原建档回执；POST `/review` 只核对完整候选，分页绑定具体新资料和所见来源；根 POST 明确保存资料、原来源/修订/核对 token、完整候选数量和无现有适用档案声明。只读 review 在正文等待后重核有效会话、角色/安全修订，不能用被撤销的旧会话取得私有候选。所有读取的迟到响应在显示前沿原行 authorization 复核责任/客户来源。

重复提交可以读取同一原成功回执，不能第二次创建客户。缓存前只排除**该次真实成功**新建的客户和 link 对原来源的自身影响，仍核对其余客户、活动/责任、当前 CSV 以及该原 link 仍为当前有效版；不同内容、撤回、移交、新 CSV 或其他来源变化拒绝。排除参数为服务端内部计算，客户端不能指定。回执仍采用不可变初版，不借当前姓名代替。无自动家庭授权、周期/到店/专业检查、预约、权益/资金或库存影响。

原名单查看与客户时间轴复用 V0.68 真实 link，返回准确原 CSV；建档回执和现有客户档案相互独立。恢复独立核对原 CSV 完整行、customer初版与原回执同一操作人/时间、原创建角色、完整建档前候选/前缀和 link 身份，初版 rowid 必须紧接建档前前缀，拒绝同毫秒后来资料替换和遗漏候选。当前工具要求schema60；旧schema59备份保持原件，用V0.68工具独立恢复后迁移，再重新备份。

四个独立虚构阶段：已建档/关联、关联已撤回但档案保留、重新关联已有新档案、后续资料修订但原初版保留。新增四客户、四原批次/回执及七link版本；原示例不重置。完整CLI核对schema60/238表（237个恢复数据表）、七活动十一版本、十二批次十三版本、十三link和四建档回执，重复初始化和独立恢复全部非会话原行/投影一致，会话0。
