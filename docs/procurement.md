# V0.39 供应商、采购需求审批与实际订货

进入「供应商与采购」，复用原商品目录的不可变版本、规格和数量单位。供应商与采购是门店业务，不借客户身份或客户专属附件存放组织资料。业务后台仍是本地开发系统；供应商资料和虚构订货不发到公开方案站点。

## 来源与商业流程

负责人维护供应商本店编号和不可变资料版本。实际联系当事人、联系方式、地址与结算资料未知时保留为空；明确供应范围、原资料说明和可核对出处。本地目录启用/停用不是正式资质或合同核验，不产生实际联系消息。

前台/负责人登记采购需求：固定供应商版本、每行本店实物商品版本、实际数量、人工整数分单价与来源。合计只作精确整数乘加，不套优惠、费用或付款规则。预计日期由实际来源填写，未知保留为空。

草稿 → 明确提交 → 负责人商业批准/驳回 → 已发生实际订货。批准和订货分别记录。订货需要人工实际时间、同一供应商外部编号与原商业批准来源；同一供应商编号不能重复登记。提交/批准/订货前，供应商和原商品版本必须仍有效；变化时明确退回草稿，追加新来源版本后重新提交审批，不能静默替换原依据。已记录实际订货不作尚未订货取消，也不补造供应商取消回执。

实际订货固定原商品数量单位与类别，后续名称/价格修订保留旧版，不能改写在途数量单位。新记录不产生销售、预留、库存收货、付款或应付账；分批验收、批号/效期/仓位、差异隔离、退供及库存入库在V0.40继续接通原账。

## 权限、历史和恢复

当前本地权限：门店负责人维护供应商及商业批准/驳回；负责人/前台保存需求和实际订货；内部人员本店读取，家长拒绝。正式采购/仓库/质量职责、预算和供应商资质仍以真实来源确定。

API GET/POST /api/suppliers、/api/purchases；/:id读取具体版本及有界历史，/:id/versions追加原来源，采购/:id/events明确submit/approve/reject/reopen/order/cancel。/api/procurement/options提供本店有效原来源，数量有上限并明确提示，不能把截断视为完整目录。状态检索、分页和全店来源序列共用，后续页不混入新版本。

读入请求体后重核当前来源，正向动作在缓存响应前拒绝已停用/改变的来源，当前会话和岗位在事务中再次检查。业务、幂等响应与审计共同回滚。SQLite原生门禁镜像身份、版本/转换、实际数量价格、商品单位和实际订货时间/来源。供应商版本与采购事件共用全店追加序列；每次事件另固定原商品版本rowid前缀，相同毫秒后来的商品或供应商不替换旧批准。

schema36五表：suppliers、supplier_versions、purchase_requests、purchase_versions、purchase_events。备份与独立恢复重放完整来源/版本、状态和精确金额，所有表与旧账一致，会话清零。非空schema35升级不补造供应商、采购审批、订货或入库。

## 展示与验收

两家虚构目录展示实际来源/未知资料，五个虚构需求展示草稿、待审批、已批准待订货、已实际订货而验收未知、明确驳回。重复初始化保存所有此前业务与人工修订，库存/资金不改变。电脑手机页面支持多行人工开单、原供应商版本、商业决定和实际订货；来源冲突保留填写并阻止静默替换，退出清除资料。
