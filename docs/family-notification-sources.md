# 服务通知固定原本人申请/回复（V0.62）

对应T08.02 / M16-F04。员工发布工作台服务通知时明确选择“不关联原申请”或“采用本人原申请/公开回复”。候选只来自同客户、同门店、该指定本人提交的原意向，包含当前原修订和对外说明；闭合或本人撤回的意向也可明确通知其事实，不当作实际预约办理。

关联保存原申请编号、原标题、种类、本人期望时间是否未知与原区间、本人原说明，以及指定原事件/修订的动作、状态、公开回复、时间和家庭/员工来源。内部核对依据不进入家庭通知快照。后来回复不覆盖旧通知来源；新版通知须手工明确采用当前原修订。关联不写原申请、不改排期、不自动占名额、请假、扣次、退款、外部送达或临床同意。

通知历史和每版主动已读仍独立；旧版已读不代替新版。家长在通知中读固定原来源，可打开原本人申请/回复入口看后来记录，界面说明原入口可能包含新回复。通知或授权撤回关闭家长访问，后来重新发布不恢复撤回原版本。员工仍保留原历史。

员工GET `/api/family-notifications/staff/:customer/:recipient/sources` 读取30至100条有界来源分页，完整总数及源指纹绑定该本人当前申请/回复；新回复或授权来源变化拒绝旧分页。POST通知沿原接口增加source_kind、source_request_id、source_request_revision：明确none或family_request。旧客户端不传这些字段兼容为不关联，不推断已有原申请即已关联。原来源当前修订在事务中再次检查；旧选择拒绝，填写保留，读取来源时保留旧选项，必须手工选择新版。

schema56增加一张不可变来源表，并给通知版本追加明确来源字段和延迟配对引用。原schema55通知事实逐字段保持，迁移只标记legacy_unknown，保存旧未追溯标记，不补造原申请链接。新增版本不得写legacy_unknown。采用原申请的通知不能提交缺失配对来源，来源插入/审计失败整份通知及幂等一起回滚；原生身份、当前原修订、公开JSON和不可覆盖保护与恢复核对一致。恢复引用旧原事件，不依今天新回复替代。

客户时间轴包含固定原申请/修订，原财务/专业权限不放宽。完整库234表（233数据表）。八独立虚构阶段包含本人提交、员工回复、结束、本人撤回、后来新回复、通知撤回/重新公开和明确不关联，重复初始化不覆盖后来事实。验证入口14项 `test/family-notification-sources.test.mjs`、`npm run test:family-notification-sources-browser`、原通知/申请回归、完整示例CLI备份恢复及全量`npm test`；结果在progress/handover。业务验收与真实外部渠道继续待完成。
