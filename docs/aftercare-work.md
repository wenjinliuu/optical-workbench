# V0.22 原件维修、复检与归还

原售后详情中的“维修批次与原件归还”接续已经实际接收的原出库商品。原退回接收事件是每个初始维修安排的固定来源，之后动作固定父维修事件，全部保留原客户、原订单版本/原行及商品版本。安排本次责任人和说明；本批次责任人或负责人开始/完成，具备复检权限人员明确项目及结论，不合格重新安排返工并再次复检；仅合格来源可记录实际原件领取人、规范UTC过去时间及签收说明。

GET `/api/aftercare/cases/:id/work?limit=50&offset=0` 返回完整分项余额、当前案例/维修版本、固定原件接收来源、可接续批次和分页历史。POST 同路径 `/events` 使用 expected_revision 与 expected_case_revision；来源、数量及案例状态任何变化均409，读取最新保留填写，失效来源不可自动替代。每次动作记录 note/reason；显式幂等键，审计与业务在同一事务提交。

| 操作 | 固定来源 | 额外字段 | 权限与状态 |
| --- | --- | --- | --- |
| plan | receive_return（return_id）；source_id=null | assignee_id / instructions | 负责人/前台，活动案例 |
| start / complete | plan / start | — | 固定批次责任人或负责人，案例处理中 |
| check_pass / check_fail | complete 或 rework_complete | checks：1–20项label/result/notes，结论与项目匹配 | 负责人/专业人员，案例处理中 |
| rework_plan / rework_start / rework_complete | check_fail / rework_plan / rework_start | 安排含assignee_id / instructions | 安排由负责人/前台，执行由固定批次人/负责人；实际执行须处理中 |
| return | check_pass | receiver_name / returned_at / receipt_note | 负责人/前台，案例处理中 |
| cancel_plan | 未开始完整plan | 整计划quantity | 负责人/前台，活动案例；已执行计划不可撤销 |

数量分为待安排、待维修、维修中、待初检、不合格、待返工、返工中、待再检、合格待归还、已归还十项，总和等于累计实际接收数量。每个父来源可拆数量，子动作累计不超过父量；已全撤销初始安排释放原接收件安排容量。维修结束不等于复检合格，复检合格不等于实际归还，结束售后沟通记录也不改变实物保管。

当前售后保管 = 累计接收 − 原件实际归还。正常可用/预留/隔离库存和资金记录不由维修动作改写。归还后同一原出库来源可在后续新案例再次退回：外部容量 = 原出库数量 + 已实际归还原件 − 累计接收退回。原案例累计接收仍不能超过原案例数量；再次服务通过新案例，连续历史保留。019替换旧退回容量触发器，018原迁移不修改，非空升级不造维修记录。

native触发器禁止更新/删除、越量、串来源、无实际退回、非法责任人/复检及虚假归还。恢复回放核对固定案例版本、父来源、明确检查、签收及十项守恒；新表纳入备份清单和客户时间轴。退出清空表单与详情，迟到的已授权响应不可恢复旧会话内容。虚构演示覆盖已安排、维修不合格→返工→合格待归还、已实际归还三类阶段；追加时不覆盖手工修改。

本路径限原件维修与归还。正式重做/换货、新商品库存、专业参数与批准、报损/退供应商、退款收费、采购批号/序列号、索赔召回和回访继续按真实规则实现。T04.05及所有整项业务验收保留待完成。
